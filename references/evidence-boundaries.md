# Evidence and claim boundaries

## Evidence classes

Classify every substantive statement before drafting:

| Class | Meaning | Report treatment |
| --- | --- | --- |
| Accepted | Current formal or reviewed project evidence | State directly within its recorded scope |
| Exploratory | Committed or recorded diagnostic evidence without formal promotion | Label as exploratory or selection-validation evidence |
| Planned | Authorized or proposed future work | Write as plan, never as a result |
| Negative or mixed | Failed hypothesis, inconsistent direction, or unresolved attribution | Preserve beside positive evidence |
| Unavailable | Missing test, timing, statistic, or protected artifact | State the absence; do not infer |

## Authority order

Prefer current repository authorities and accepted reports over chat recollection. When available, read:

1. repository-scoped `AGENTS.md`;
2. `docs/PROJECT_CORE.md`;
3. `docs/CURRENT_STAGE.md`;
4. experiment or review records named by those authorities;
5. the current DOCX being revised.

Verify Git identity and worktree state. If an exploratory commit differs from the accepted-code identity, keep both facts separate.

## Claim ceiling

Before writing conclusions, create two lists:

- supported claims;
- prohibited or not-yet-supported claims.

Do not convert non-significance into equivalence, one favorable dataset into global superiority, candidate diversity into predictive adequacy, or missing timing into a speed claim. A closest-work search that found no exact match does not prove novelty.

## Protected and irrelevant material

Do not expose credentials, private URLs, raw protected predictions, patient-level data, platform request details, retries, or internal task logs. Engineering facts may support audit but normally do not belong in the advisor-facing narrative.
